# Handoff: state of the project and what comes next

Written 2026-10-03, for release **v0.1.0**: the first stable foundation. Read
[CLAUDE.md](CLAUDE.md) first for the architecture, invariants and checks.

## The project and its owner's decisions

The app generates audio dramas. A React timeline holds voice, music and sfx
clips, all generated by local models: Chatterbox (TTS), ACE-Step 1.5 (music)
and Stable Audio 3 (sfx and music). They run behind a FastAPI gateway, on an
RTX 5090 (32 GB, Blackwell sm_120) passed through to a Proxmox VM.

Decisions already made by the owner. Don't relitigate them without asking:
- **Local first.** ElevenLabs is optional and never an automatic fallback.
- **Quality first; licensing comes later.** Chatterbox and ACE-Step are MIT;
  Stable Audio 3 is free below $1M a year in revenue.
- **Ollama runs on CPU, in system RAM.** The host has 256 GB; the GPU VM gets
  64–128 GB. The 5090 is reserved for audio.
- **Docker with CUDA on the VM** is the deployment. The Mac's Docker is for
  development only, using placeholder stubs.
- **An in-app LLM "director" is planned:** story → cast → cues → timeline (M4
  below).

## What is verified

- **Backend:** 150 pytest tests, no GPU or torch needed. They cover the API end
  to end through the job queue, gateway routing and readiness, provider
  lifecycle and lock behaviour, the job lanes, the RNG lock, cross-process GPU
  slots, the ElevenLabs credential gate, the Stable Audio 3 shared pipeline,
  stall regressions, contract signatures and default drift. Every regression
  test was mutation-checked: re-breaking the fix makes it fail.
- **Frontend:** 91 vitest tests (client, store, trim and schedule math,
  engine, panel, timeline). Lint and build pass.
- **Dependencies:** all three GPU dependency sets resolve wheel-only for
  x86_64/py3.12/cu128, with the torch pins honoured.
- **Dev stack:** the stub stack passes `scripts/smoke_gpu.py --dev` end to end
  in CI. That covers the built images, gateway, model service, readiness and a
  restart.

## What is NOT verified: treat these as open risks

1. **Nothing has run on the GPU.** The model loads, VRAM use, audio quality
   and the cu128 wheels on sm_120 are all untested. The contract tests prove
   call signatures, not behaviour or value types. The first real run is
   `python3 scripts/smoke_gpu.py` on the VM. It needs `HF_TOKEN`, the Stable
   Audio 3 licence accepted on Hugging Face, and roughly 31 GB of downloads.
2. **The frontend has not been clicked through in a real browser.** This
   covers #7's "only cloud can serve" picker state and #12's playback and trim
   fixes. Playback is unit-tested against a fake `AudioContext`; real browser
   scheduling, autoplay resume and fade ramps need a manual check.
3. **Snapshots cover pinned versions only.** The diffusers snapshot is of the
   declared floor (0.40.0). A newer diffusers in the image could differ.
4. **The `--no-deps` model packages' imports** are never exercised outside the
   GPU image. `check_deps.py` covers resolution, not imports.

## Review priorities (where a fresh reviewer adds the most)

1. **#12, the playback engine** (`frontend/src/engine/`,
   `components/Timeline.tsx`, `lib/trim.ts`). These are the most intricate
   changes and are only fake-tested. Review the scheduling maths and fade
   automation against the Web Audio spec, and the IndexedDB → server re-fetch
   fallback.
2. **#10, the contract-test machinery** (`scripts/snapshot_contracts.py`,
   `backend/tests/test_contracts.py`). This is an AST resolver and fake-module
   builder. Look for ways it gives false confidence: symbols resolved to the
   wrong definition, or calls that bind but would fail at runtime.
3. **Concurrency** (#6, #4): `Provider` locking, `rng_scope`, `gpu_slot`, the
   Stable Audio 3 shared pipeline, the job-queue lanes. Look for races and
   deadlocks between the sweep, loads and generations.
4. **The gateway** (#7): the readiness semantics, the discovery cache, and
   `_LAST_OWNER` routing when upstreams restart.
5. **Security:**
   - the API-key middleware and its open paths
   - CORS defaults
   - voice-reference uploads (size, type, consent text)
   - `storage._safe` path validation
   - the ElevenLabs key staying server-side
   - ports bound to loopback, and nginx not injecting the key
6. **Known bugs, scheduled for v0.1.1.** Claude fixes these right after
   v0.1.0, test-first, one PR each. Check `main` and the CHANGELOG before
   starting one. Until then they are open:
   - **ElevenLabs lengths are wrong in the API.** ElevenLabs returns mp3, and
     only WAV duration is measured server-side:
     - `ElevenLabsVoice` reports `duration=0.0`, and `ElevenLabsSfx` reports
       the *requested* length.
     - The timeline is unaffected, because the generation panel decodes the
       audio when the length is 0 (`GenerationPanel.tsx` around line 133).
     - Any other API consumer gets the wrong value. That includes the planned
       director, which lays out lines by their measured length.

     Measure mp3 duration server-side.
   - **Eviction reorders the job list.** In `JobQueue._evict`, when the oldest
     job is still live it is moved to the end of the order and eviction stops.
     That reorders `GET /v1/jobs` and can stop eviction early.
   - **Providers never report progress.** `job.progress` jumps from 0 to 1, so
     the UI can't show anything for minutes-long music jobs. The v0.1.1 fix
     reports honest phases plus elapsed time. Step-level progress from inside
     the models needs hooks into their libraries that can only be verified on
     the GPU, so it stays an M3 follow-up.

## Foundational backlog, in plan order

The full approved plan, with rationale, is in [docs/plan.md](docs/plan.md).
The essentials are below. Items marked **[GPU]** need the VM's results first.

- **M2. The first GPU run [GPU, owner].** Run `scripts/smoke_gpu.py` and keep
  `smoke-results/*/results.json`. Its cold, warm and load timings and its VRAM
  peaks drive M3. It may also force the split topology (`--split`).
- **M3. Hardware tuning [GPU]:**
  - **Ollama:** add it as a compose `llm` profile, hidden from the GPU: no
    reservation, plus `NVIDIA_VISIBLE_DEVICES=void` and
    `CUDA_VISIBLE_DEVICES=`. Pin its version, set `mem_limit`,
    `OLLAMA_MAX_LOADED_MODELS=1`, and use an 8–14B quantized model.
  - **VRAM budget:** set it from M2's measurements. Start with Chatterbox +
    Stable Audio 3 medium (one checkpoint for both tracks) + ACE-Step 2B with
    the 1.7B LM.
  - **VRAM-aware eviction:** check `mem_get_info` before a load and evict
    least-recently-used idle providers, but only if bigger checkpoints are
    wanted.
  - **Optional RAM parking tier:** `park()`/`unpark()` with a RAM budget. Build
    it only if warm reloads from the page cache prove slow.
  - **ACE-Step offload flags:** expose them as environment variables
    (`acestep.py`).
- **M4. The director**, as its own service (an upstream named `director`, so
  `director:` job ids route unchanged):
  - **LLM client:** Ollama's native `/api/chat`, with a JSON-schema `format`,
    `num_ctx` set per request and `think:false`.
  - **Script:** the LLM emits an ordered script (lines, sfx, music
    start/stop, ambience, pauses), and the server derives timing anchors.
  - **Casting:** Chatterbox has a single built-in voice; every other voice is
    a clone of an uploaded sample. So each character needs a voice reference.
  - **Rendering:** voice first, so measured line lengths fix the layout. Clamp
    lengths to each provider's bounds (trim if too short, crossfaded segments
    if too long). Seeds come from `hash(plan_seed, cue_id)`. A resumable
    per-cue manifest is kept under `/data/director/`.
  - **Frontend:** a `/director` page (story → script → casting → render →
    import).
  - **Evals:** golden stories behind `@pytest.mark.llm`; CI uses recorded
    responses.
- **M5. Finish the loop:**
  - **Mixdown/export:** server-side, from stored audio, applying gain and
    fades.
  - **Server-side projects:** clips already carry `audioId` (#12), so this
    mostly means storing the document.
  - **Undo/redo.**
- **Foundation gaps outside the plan:**
  - The job queue lives in memory, so a restart loses job state.
  - No retention or cleanup for generated audio.
  - No Python lockfile (`uv lock`).
  - Frontend types are not generated from OpenAPI.
  - No structured logging or metrics.
